# Daox

**Languages:** [English](https://github.com/soysouvanh/lightx-js/blob/main/packages/daox/README.md) | [Français](https://github.com/soysouvanh/lightx-js/blob/main/packages/daox/README.fr.md)

**Daox** is a **“Bare-Metal” and Database-First** ORM for Node.js and TypeScript, designed from scratch to achieve absolute pure performance and strictly zero overhead.

Unlike traditional ORMs that rely on heavy runtime reflection and complex object mapping (Classes, Decorators, Proxies), Daox operates differently. It introspects your existing database **Ahead of Time (AOT)** and generates pure, frozen, optimized, and statically bound TypeScript code.

Forged for the LightX ecosystem, Daox scales safely from lightweight applications to extremely high-frequency transactional APIs.

---

## Core principles

### Zero-overhead runtime (AOT-driven)

Daox removes the "abstraction tax". There is absolutely no metadata parsing, no decorator reflection, and no global ORM engine running in your application's RAM. Files generated by Daox are in native TypeScript and surgically invoke the C++ SQL Drivers.

### Military-grade security

Built to be impenetrable. All schema constraints, table identifiers, and parameters are structurally escaped during the _Build_ process. The framework fully neutralizes Prototype Pollution vectors, wild evaluations, or Remote Code Execution (RCE) via syntax injection. Furthermore, SQL bindings rely exclusively on the native parametrization of C++ drivers (No raw SQL string concatenation).

### Zero-allocation streaming

Daox defaults to continuous native streaming in `AsyncIterable` via structural cursor iteration (`for await (const row of streamer)`). Mathematically, this guarantees that retrieving 10 rows or 2,000,000 rows consumes the exact same finite memory footprint (O(1)), making OOM (Out Of Memory) crashes virtually impossible.

### Stateless architecture (executor injection)

Daox-generated code **contains no connection strings or underlying global state**. It strictly uses an **Executor Injection** pattern. You instantiate a native pool (like `better-sqlite3` or `postgres`) independently of Daox, then explicitly pass this connection pointer to your queries. This allows native support for transactions and Edge Serverless infrastructure right out of the box.

## Getting started

### 1. Generate your DAOs (data access objects)

Daox is _Database-First_. Therefore, it requires access to a working database to build itself. It automatically infers the engine from the provided URL and generates an ultra-scalable file architecture in `./src/dao/` by default.

```bash
# PostgreSQL
npx @soysouvanh/daox generate --url="postgres://admin:pass@localhost:5432/my_db"

# MySQL / MariaDB
npx @soysouvanh/daox generate --url="mysql://admin:pass@localhost:3306/my_db"

# SQLite
npx @soysouvanh/daox generate --url="sqlite://./playground.db"

# Microsoft SQL Server
npx @soysouvanh/daox generate --url="sqlserver://admin:pass@localhost:1433/my_db"

# Oracle DB
npx @soysouvanh/daox generate --url="oracle://admin:pass@localhost:1521/my_db"
```

### 2. Leverage the generated architecture

Your `./src/dao/` directory now encapsulates our ultra-strict TypeScript Iterators split file-by-file, modeled precisely against your database.

```typescript
import postgres from "postgres";
import { PostgresExecutor } from "@soysouvanh/daox";
import { UsersDao, User_rolesDao } from "./dao/index.js";

// 1. Initialize the Native Driver & Push it into our Executor
const sql = postgres("postgres://admin:pass@localhost:5432/my_db");
const exe = new PostgresExecutor(sql);

async function bootstrap() {
  // Strictly Typed Insertion
  const user = await UsersDao.insert(exe, {
    email: "hello@lightx.io",
    status: "active",
  });

  // High-Performance O(1) RAM Streaming
  for await (const row of UsersDao.listByCursor(exe, null, 100)) {
    console.log("Iteration without RAM overhead :", row.email);
  }
}

// 2. Explicit Transaction Example: Perfect Isolation (Atomicity)
async function securedTransaction() {
  // For granular manual control, retrieve a native transaction pointer
  const txClient = await sql.reserve();
  const txExe = new PostgresExecutor(txClient);

  try {
    await txExe.query("BEGIN"); // Start of the transaction

    const admin = await UsersDao.insert(txExe, {
      email: "admin@sec.com",
      status: "active",
    });
    await User_rolesDao.insert(txExe, {
      user_id: admin.id,
      role_name: "super_admin",
    }); // Dependent action

    await txExe.query("COMMIT"); // Commit
    console.log("Atomic transaction successfully completed.");
  } catch (err) {
    await txExe.query("ROLLBACK"); // Absolute cancellation in case of breakage
    console.error("Critical failure handled, Rollback executed :", err);
  } finally {
    txClient.release();
  }
}
```

### 3. Exhaustive dictionary of the auto-generated API

The Daox engine strictly applies the **YAGNI** (You Aren't Gonna Need It) concept. The injected DAO interface depends meticulously on the topology of your SQL table in the actual database.

### Global methods (Always generated)

These methods exist for all tables (and insertable Views), regardless of their internal structure.

#### 1. `insert(exe, data)`

Performs a strict unitary insertion, returns the typed inserted row. Intelligently omits auto-increments and auto-generated timestamps from the required parameters.

```typescript
const user = await UsersDao.insert(exe, {
  email: "hello@lightx.io",
  status: "active",
});
```

#### 2. `insertBatch(exe, items[])`

Executes ultra-fast bulk insertion by dynamically generating sequential transactional descriptors for 1,000 or 100,000 rows (`INSERT INTO ... VALUES (), (), ()`).

```typescript
await UsersDao.insertBatch(exe, [
  { email: "a@test.com", status: "active" },
  { email: "b@test.com", status: "suspended" },
]);
```

#### 3. `count(exe)`

Retrieves the exact total number of rows currently in the table. Returns an integer scalar.

```typescript
const totalUsers = await UsersDao.count(exe);
```

### YAGNI methods (Generated via Primary Key)

If (and only if) the table has a **unique Primary Key** (e.g. `id`), the generator extends the DAO with these methods.

#### 4. `findBy[Pk](exe, pk)`

Surgically retrieves a record by its absolute key. Returns the entity or `null`.

```typescript
const user = await UsersDao.findById(exe, 42);
```

#### 5. `existsBy[Pk](exe, pk)`

Performs a lightweight boolean check to see if a record exists by its Primary Key, without fetching any payload data.

```typescript
const exists = await UsersDao.existsById(exe, 42);
```

#### 6. `updateBy[Pk](exe, pk, patch)`

Dynamically updates the target record. It constructs a strict `UPDATE ... SET` query limiting network traffic exclusively to the explicitly provided payload.

```typescript
await UsersDao.updateById(exe, 42, { status: "deleted" });
```

#### 7. `deleteBy[Pk](exe, pk)`

Radically deletes the targeted row via its absolute Primary Key.

```typescript
await UsersDao.deleteById(exe, 42);
```

#### 8. `listByCursor(exe, lastCursor, limit)`

Deploys the `AsyncIterable` iterator targeting the primary key to stream the table millions of times with zero live memory footprint (RAM) ($O(1)$) via a `WHERE pk > cursor ORDER BY pk ASC` scroll.

```typescript
for await (const row of UsersDao.listByCursor(exe, null, 1000)) {
  console.log(row.id, row.email);
}
```

#### 9. `listByOffset(exe, offset, limit)`

Retrieves records using traditional skip clauses (Offset Pagination). Useful for specific UI use-cases requiring arbitrary page jumps over a smaller dataset.

```typescript
const page = await UsersDao.listByOffset(exe, 0, 50);
```

### Topological YAGNI methods (Generated via Indexes)

Daox introspects your SQL indexes (native and foreign keys). The API interface mathematically aligns with the pre-existing read highways in your database.

#### 10. `existsBy[Cols](exe, col1, col2)` (All Indexes)

**(For ALL indexes).** Performs an ultra-fast existence check via an index, returning a boolean without reading the row.

```typescript
// Generated because an index (unique or not) exists on your table
const exists = await UsersDao.existsByEmailAndTenant(exe, "admin@x.com", 1);
```

#### 11. `findBy[Cols](exe, col1, col2)` (Unique Index)

**(If the DB Index is UNIQUE).** Executes a filter returning at most **one** single deterministic row.

```typescript
// Generated because a UNIQUE index (email, tenant_id) exists on your table
const account = await UsersDao.findByEmailAndTenant(exe, "admin@x.com", 1);
```

#### 12. `findAllBy[Cols](exe, col1, col2)` (Classic / Multiple Index)

**(If the Index is NOT UNIQUE).** Executes an optimized extraction returning an **array** of entities (e.g. a simple index or a FK).

```typescript
// Generated because a simple Index (status, role) was placed on this table
const admins = await UsersDao.findAllByStatusAndRole(exe, "active", "admin");
```

#### 13. `countBy[Cols](exe, col1, col2)` (Classic / Multiple Index)

**(If the Index is NOT UNIQUE).** Rapidly counts the number of records matching the index criteria.

```typescript
const activeAdminsCount = await UsersDao.countByStatusAndRole(
  exe,
  "active",
  "admin",
);
```

### Iso-Generated Unit Tests

During the codebase compilation, Daox strictly generates an isometric Unit Test file matching the exact structure of your DAO classes. It provides decoupled Jest test environments out-of-the-box that assert the strict invocation logic of your `GenericExecutor`, fully isolating your database logic without any manual test writing.

**Location of generated tests:**
The tests are systematically generated directly alongside your DAO files in your specified output directory (default: `./src/dao/`).
For a table named `users`, you will find `./src/dao/users.dao.test.ts` paired with `./src/dao/users.dao.ts`.

**How to run them:**
Because they are fully typed and decoupled, they can be executed seamlessly using popular test runners like Jest or Vitest without any complex database or mock configuration.

```bash
# Run all auto-generated DAO tests using Jest
npx jest src/dao/

# Or run them with Vitest if you prefer
npx vitest run src/dao/
```

Daox acts as the orchestrator for the fastest C/C++ Node.js drivers. Be sure to install the desired native _Driver_ (peer-dependency) based on the engine:

| SQL Dialect            | URL Prefix                 | Required NPM Package (peer dependency) |

| **SQL Server / MSSQL** | `mssql://`, `sqlserver://` | `mssql`                                |

## Advanced concepts

### Transaction management (native isolation)

Thanks to the strict **Executor Injection** pattern, the transactional mechanism does not incur any OS overhead. Simply bind the current transaction using a new local Executor, then pass it dynamically to your methods.

```typescript
await sql.begin(async (txSql) => {
  // Locking the Transaction in the local Executor
  const txExe = new PostgresExecutor(txSql);

  // Both operations are now atomic and isolated without any ORM overlay!
  const user = await UsersDao.insert(txExe, {
    email: "transaction@lightx.io",
    status: "active",
  });
  await User_rolesDao.insert(txExe, { user_id: user.id, role_name: "guest" });
});
```

### The built-in YAGNI concept

(_You Aren't Gonna Need It_). Daox strictly generates the essentials. For instance: if a View (`VIEW`) in your DB does not materialize a primary key, Daox will only compile reading and streaming read functions (`listByCursor`), flatly refusing to create `updateById` methods or arbitrary deletions. The mathematical rigidity of the system takes absolute precedence.

### DAO Overrides (Custom business logic)

While Daox generates all your DAOs, many use-cases require injecting complex business queries (e.g. INNER JOIN, aggregations) or overriding a specific generated method to mandate a behavior.
The `src/dao_overrides/` directory was created specifically for this purpose. It allows you to create "mirror" classes that will seamlessly replace or extend default generated methods during the _AOT Build_, without losing the compiler's structural integrity.

**[View the explanatory documentation and ready-to-use examples for Overrides](./src/dao_overrides/README.md)**

## Testing Environment (Unit & Integration)

To guarantee its "Zero-Fail" parametric rigor, Daox includes a comprehensive test suite.

### 1. Unit Tests (AOT & Security)

Unit tests verify the SQL scanners, Anti-SSRF security, Path Traversal protections, OOM safeguards, and the SOTA generators.

```bash
npm run test:unit
```

### 2. DB Integration Tests (Multi-Dialect)

Integration tests validate the entire Daox compilation directly against real, isolated databases (via Docker Compose).

Ensure that a Docker daemon context is available, then:

```bash
# Boot up the Docker infrastructure (MySQL, Postgres, SQL Server, Oracle)
npm run test:db:up

# Execute all Bare-Metal integration tests across the 5 drivers
npm run test:integration

# Wipe and teardown the Docker infrastructure
npm run test:db:down
```

_(All connections to the test instances, including the volatile SQLite DB, are architecturally centralized in the internal `tests/db_config.ts` file)._
